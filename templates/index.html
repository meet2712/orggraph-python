      The high precision comes with lower coverage: the rules leave uncertain managers open rather than add a weak edge. These synthetic-data results do not establish accuracy on real company records. The benchmark CSV is used only by the offline evaluator.

      What the evidence score means

      The score reflects title seniority, functional match, and team scope. It is a heuristic, not a calibrated probability. A link is accepted only when its score reaches {{ threshold.score|percent }} and exceeds the next candidate by {{ threshold.margin|points }} percentage points. The separate generated answer file can be used for offline accuracy checks; it is not stored in the app database.

      How it works

      From job titles to reporting lines

      The database starts with a flat employee list. SQL views interpret each row and calculate reporting lines whenever the source changes.

      1. Generate messy source records

      The Python generator creates {{ dataset.companies|count }} companies and {{ dataset.employees|count }} employees with varied functions, seniority, team sizes, missing fields and title noise. The generated answer key is stored separately in a CSV for offline evaluation. It is never imported into the operational database or used to choose a manager.

      2. Calculate the hierarchy in SQL

      01 · Input

      Read source rows

      companies and employees are the only persisted tables. Titles, department, team and location remain as observed.

      02 · Parse

      Infer role level

      employee_features normalizes title abbreviations and derives seniority and function from source fields.

      03 · Compare

      Rank candidates

      Only plausible leaders in the same company are considered. Seniority, team scope and function determine the evidence score.

      04 · Decide

      Accept or abstain

      reporting_predictions compares the top candidates. It creates an edge only when the score and the lead over second place both clear their thresholds.

      Evidence scorescore = strongest matching hierarchy/team rule + location tie-break

      The SQL CASE order sets the main score. Location contributes a small tie-break. The score is not a calibrated probability.

      Lead over next candidatelead = top score − second score

      If two candidates look too similar, the SQL rules leave the manager unresolved.

      Acceptancescore ≥ {{ threshold.score|percent }} AND lead ≥ {{ threshold.margin|points }} points

      Thresholds are visible in the inference_settings view and decision audit.

      3. Inspect the decision

      employee_reporting_audit joins the raw employee row with inferred features, the selected manager or leading candidate, score, margin and decision reason. company_profiles and company_metrics calculate headcount, size band and coverage from current rows. Each app page runs a company-scoped SQL form of the same inference rules for speed.

      Open the schema page to read every CREATE VIEW statement, or run a query in the database explorer.

      4. Check quality separately

      The generated answer CSV can be compared with the SQL view output outside the app. This avoids putting employee-to-manager answer mappings in the operational database. Coverage describes how many lines were accepted; precision requires that separate answer key. A high evidence score alone does not prove a correct manager.
